## 1. 设计概述

- 1.1 设计目标：把 SRS 的能力落成可实现的架构与模块，重点覆盖三权分立、默认拒绝、SSO 三重角色、任务中心、审计留痕
- 1.2 设计约束（来自 SRS，逐条列为**硬约束**）
  - 认证不可用时上层业务**拒绝登录、既有会话失效**，不得降级为免认证（OI-G-004）
  - 授权 = **能力维度（用户组→角色）× 范围维度（用户组→资源组）**，二者缺一即拒绝；账户→用户组→角色/资源组，**账户不直接持有角色或资源组**
  - 一个账户**只能归属一个用户组**；用户组可绑多角色、关联多资源组（并集）
  - 三权分立互斥（系统管理员 ∩ 审计管理员）**在角色绑定环节阻断**
  - 授权关系变更**即时生效**：受影响在线用户会话立即置过期，强制重新登录
  - 角色全部内置、权限范围运行时只读；架构须保留运行期自定义角色的扩展能力
  - 资源清单由上层业务注册查询接口、OMS 回调获取；**归属关系 OMS 侧只读**
  - 密码/凭据/密钥加密存储，明文不落日志；全链路加密，服务间通信证书由 M13 统一管理
  - OMS 自身功能**不因 License 未授权/过期/吊销而受限**（是否限制由上层决定）
  - **部署基线**：OMS 与 Nginx 以容器化方式部署在 Kubernetes 集群；数据库数据、运行日志与备份包落 **PVC**，应用配置落 **ConfigMap**，证书与密钥/凭据落 **Secret**
  - **扩展性要求**：当前不要求**单实例多副本**，但应用须**无状态化**设计，保证后续可通过 HPA/多副本扩展（会话可外置、文件存储可抽象、定时与任务可选举/加锁）
  - **同集群多实例**：同一 K8s 集群允许部署多套 OMS，**每个命名空间最多一套**；命名空间即实例边界，实例间**不共享有状态资源**；禁用 ClusterRole/CRD/固定 NodePort/静态 PV 等集群级单例资源，所有资源命名空间内闭环（HLD 10.9、ADR-015）
- 1.3 设计原则：模块化单体/分层、无状态化 + 外部化状态、配置驱动、能力可插拔（上层业务模块注册区）、失败明确不降级、审计优先
- 1.4 设计范围与非范围：不含上层业务逻辑与业务数据；不含 SCC 内部算法实现；不含《接口/数据库/部署》文档的明细
- 1.5 关键设计决策（ADR）索引表：每条=问题 / 备选 / 结论 / 理由 / 影响章节（初稿见第 14 章）

  > ① **Spring Boot 4.0.7 生态兼容性**——Boot 4 是主版本跃迁，Spring Security 配置 API 与第三方 starter（**MyBatis 集成层**、ShedLock、springdoc-openapi、Micrometer 周边）的版本线需逐个验证；验证不通过的项在本表内替换为备选，并记录 ADR。

  > ③ **MyBatis 3.5.19 与 Boot 4 的集成层**——3.5.19 是 **MyBatis core** 的版本；与 Spring 的粘合由 `mybatis-spring`（或 starter）承担，该集成层对 Spring Framework 7 的支持版本线**必须实测**。若同时使用 **MyBatis-Plus**，其自身会传递引入某个 mybatis 版本，需用 `dependencyManagement` 把 `org.mybatis:mybatis` **钉到 3.5.19** 并验证兼容性（MyBatis-Plus 与 MyBatis core 的版本号体系是两套，不可混用）。**分页实现方式**（手写 `limit/count`、PageHelper、或 MyBatis-Plus 分页插件）须在数据访问层统一约定，避免各模块各写一套。
  > ④ **PostgreSQL 15.12 的补丁策略**——15.12 作为**交付基线版本**；PG 的**安全修复只随小版本发布**（例如 15.13、15.14…），因此不能长期冻结：需约定「基线锁定 15.12 + 安全补丁随 15.x 小版本滚动升级」，并明确升级前的回归范围（备份/恢复、迁移脚本、大表查询）。数据库大版本（16/17）变更须走 ADR。

- 4.4 三方开源组件清单与许可证合规审查（白名单 + 商用中间件单独登记）
- 4.5 兼容基线矩阵：**容器基础镜像**（openEuler 24.03 SP3；单一基线）与 **宿主架构/内核/设备**（宿主 OS 版本不作为兼容维度；**架构仅 aarch64/ARM64，不构建多架构镜像**）、K8s 发行版、数据库、浏览器、被集成第三方（SNMP 版本、SFTP 版本、CA 类型、PKCS#11、上游认证协议）
- 4.6 **密码与证书组件**：**镜像构成表**（JDK+BC 同在应用镜像、OpenSSL 每镜像各一份、Job 复用应用镜像）、术语（密码令牌）、**证书与 PKCS#11 分层且只启用第一层**（BC 编解码 + 软件密钥签名 ✅ / BCPKCS11 ⏸ / openssl-pkcs11 ⏸）、**BC artifact 表**（`bcprov`/`bcpkix`/`bcutil` 必需，`bcpkcs11` 预留）、**启用 HSM 时的落地清单**、**SCC 算法表与集成约束**
- 4.7 待定项与 ADR：是否引入 MQ、是否用 ingress-nginx、首发数据库（PostgreSQL vs MySQL）、国密是否首发必需
- 4.8 调度方案说明（**ADR-001**）：OMS 共 18 处定时/周期需求，归为周期调度、延迟重试、时间点判定、到期判定四类；首发采用 `@Scheduled` + ShedLock（仅覆盖「同一时刻单节点执行」语义），封装 `SchedulerPort`（`schedule/triggerNow/cancel`）隔离实现；Quartz 作为升级路径保留，触发条件：需要运行期任务管理/改 cron、定时任务数 > 50、要求错过补跑、需要严格故障转移语义。延迟重试类（SLO 通知、SNMP 上报、SFTP 上传、日志补报、日志接收）用「待办表 + 定时扫描 + 退避重试」实现，不占用调度框架；用户可配时间（备份计划）与屏蔽规则起止用**每分钟调度滴答 + 到点判定**，避免运行期动态注册任务；周期与阈值每轮从 ConfigMap 读取，保证调整后下一周期生效
- 4.9 数据库变更管理说明（**ADR-011**）：**不采用 Flyway / Liquibase**，改为「SQL 脚本 + 启动时执行器」。**执行模型（已确认）**：脚本在 **Pod 创建 / 重启后按顺序执行**，承担**建表与预置数据**，必须**幂等可重复执行**；库表**结构迁移只在版本升级时发生**——升级同样是"新镜像换 Pod"，因此两者共用同一入口。脚本目录与命名**沿用 Flyway 规范**（可移植，将来若引入 Flyway 可只换 runner）。

  **两级脚本模型**：

  | 级别 | 何时执行 | 脚本要求 | 典型内容 |
  | --- | --- | --- | --- |
  | **A 引导脚本**（bootstrap） | **每次** Pod 启动 | **全量幂等**：`CREATE TABLE/INDEX IF NOT EXISTS`、`INSERT ... ON CONFLICT DO NOTHING / DO UPDATE` | 建表建索引、内置角色/用户组/菜单权限点、默认策略 |
  | **B 版本变更脚本**（migration） | 启动时，**按执行标记只跑一次** | 允许非幂等（改类型、删列、加约束、数据回填） | 版本升级带来的结构变更与数据迁移 |

  **为什么 B 级仍需"执行标记"**：`ADD COLUMN IF NOT EXISTS` 可以幂等，但 **`DROP COLUMN`、改类型、加非空约束、数据回填（`UPDATE`）无法用"IF NOT EXISTS"表达幂等**——每次启动重跑会反复覆盖数据或在第二次执行时失败。因此保留一张极简 `schema_change_log`（脚本标识 + 校验和 + 执行时间 + 执行人 + 结果）作为"只执行一次"的依据；这就是 Flyway 的最小内核，也是与 A 级的唯一区别。

  **并发与就绪**：多副本同时启动时用 **`pg_advisory_lock`** 串行化（`CREATE TABLE IF NOT EXISTS` 在并发下仍可能因 `pg_class`/`pg_type` 竞态报错）；脚本未执行完成的 Pod **不进入 Ready**（readiness 门禁），避免半成品 schema 对外服务。

  **滚动升级的向前兼容（硬约束）**：升级期间新旧 Pod 并存，结构变更须遵循 **expand → migrate → contract**：先加列/加表（旧代码可忽略）→ 代码切换 → 下一版本再删旧列。**禁止同一版本内"加新列 + 删旧列"**。

  **凭据隔离**：执行 DDL 使用**独立迁移账号**（凭据入 Secret），业务运行使用仅 DML 的低权限账号，二者分离，避免运行账号长期持有 DDL 权限。

  **失败与长耗时**：脚本失败 → 该 Pod 启动失败并告警、不进入 Ready，已成功脚本可续跑；大表回填等长耗时变更**建议转 K8s Job** 执行（避免阻塞启动、触发探针超时与 CrashLoop）；每版本提供回滚脚本，**禁止运行期自动 DDL**（仅启动引导与版本变更两个入口）。

  > **启动时执行器必须提供的能力清单（缺一即视为降级为"人工执行 SQL"）**
  >
  > | # | 必须提供的能力 | 对应 Flyway 能力 | 不做会出的事故 |
  > | --- | --- | --- | --- |
  > | 1 | 按**版本号数字序**顺序执行 | `migrate` | 漏执行、顺序颠倒、字符串排序把 `V1.10` 排在 `V1.9` 前 |
  > | 2 | A 级脚本**全量幂等**，可无脑重跑 | `migrate` 幂等 | 每次重启重复插入、重复建表报错 |
  > | 3 | B 级**执行标记**：脚本标识 + **校验和** + 执行时间 + 执行人 + 结果 | `flyway_schema_history` | 非幂等变更被重复执行、数据被反复覆盖 |
  > | 4 | **校验和比对**，已上线脚本被改动则拒绝启动 | `validate` | 环境间结构不一致，线上与新环境建出的库不同 |
  > | 5 | **并发锁**（`pg_advisory_lock`），多副本只有一个执行 | 迁移锁 | 多副本并发 DDL 竞态报错、半成品 schema |
  > | 6 | 失败中断 + 失败记录 + 可续跑 + **修复入口** | `repair` | 卡在失败状态无法继续，只能人工连库改表 |
  > | 7 | **就绪门禁 + 启动自检**（schema 版本与镜像版本一致） | 间接达成 | 半成品 schema 对外服务；新镜像配旧库 |
  > | 8 | **存量库基线**（11.B 首次纳管后只走增量） | `baseline` | 存量库无法纳入版本管理，只能继续人工维护 |
  >
  > **已知代价**：第 1～8 条全部要自研，且失去 Flyway 的生态（命令行工具、`info` 可视化、社区踩坑经验）；因此必须配套"脚本评审 + 双人复核 + 生产禁手改脚本"的流程约束。

  | 缓存 | **自建** StatefulSet + PVC，镜像 **redis:7.2.12** | 会话热缓存、计数、验证码、限流；数据可重建；**不使用云托管/外部实例** |
  | 运行日志包 / 备份包 | PVC（+ 可选对象存储） | OMS 本地产物目录，抽象为存储接口 |
  | 应用配置 | ConfigMap | 非敏感配置（含 License 检查周期等后台配置项） |
  | 证书 / 私钥 / 口令 / 密钥 | Secret（或外部密钥管理） | Nginx 证书、SFTP/DB 凭据、License 校验材料；不以明文进镜像或 ConfigMap |

## 11. 升级兼容性与数据迁移

### 11.A 版本升级与兼容

- 11.1 版本与兼容性策略：应用版本号规则、接口版本与兼容窗口、**内置角色/权限点/菜单随版本注册**的兼容规则、上游认证协议与下游客户端接入的兼容
- 11.2 升级流程设计：升级前备份 → **滚动更新（新 Pod 启动时执行 A 级幂等引导 + B 级版本变更脚本，带 `pg_advisory_lock` 与就绪门禁）** → 校验 → 自检 → 失败回滚；**静态资源由发布 Job 先发布并原子切换 `current`，再切流量**；结构变更遵循 expand → migrate → contract 向前兼容，保证新旧 Pod 并存期可用
- 11.3 数据结构变更与迁移框架（**ADR-011：不用 Flyway，采用 SQL 脚本 + 启动时执行器**）：**两级脚本模型**（A 级引导脚本每次启动全量幂等执行：建表/索引 + 预置数据；B 级版本变更脚本按 `schema_change_log` 标记只执行一次）；脚本目录与 **Flyway 兼容命名**（`V<版本>__<描述>.sql` / `R__<描述>.sql` / `U<版本>__<描述>.sql`）；**顺序执行与版本号数字序**、**校验和比对**、**`pg_advisory_lock` 并发串行化**、**就绪门禁与启动自检**（schema 与镜像版本一致，不一致拒绝进入 Ready 并告警）；失败中断与断点续跑、**修复入口（对标 `repair`）**、**基线机制（对标 `baseline`，服务 11.B 存量库首次纳管）**；长耗时回填转 K8s Job；每版本回滚脚本与向前修复策略；**预置数据的覆盖边界**（随版本受控的内置角色/菜单/权限点可补齐覆盖，用户可能修改过的策略与业务数据只插不改）；脚本评审与双人复核、生产禁止手改脚本；PG 约束（`CREATE INDEX CONCURRENTLY` 等不可事务化语句的单独处理）；
- 11.4 内置数据与配置迁移：默认策略、内置账户/用户组、菜单与权限点、i18n 文案键、枚举字典的增删改
- 11.5 数据兼容与不丢失保证：SRS 4.2「升级过程中既有数据不丢失」的验证方式（行数/校验和/抽样比对）
- 11.6 降级/回滚设计：可回滚边界、不可逆变更的标记与处置、镜像与 schema 双向回滚、备份包恢复
- 11.7 备份包与配置的跨版本兼容：备份包格式版本、旧包在新版本恢复的支持范围
- 11.8 升级测试矩阵与验收清单（N-1 → N、跳版本升级、迁移中断恢复、滚动期间多副本一致性）—— **【FIG-ACT-03 版本升级流程（含回滚）】**

## 12. 安全设计专项

- 12.1 威胁建模（STRIDE）与攻击面清单：认证、会话/密码令牌、越权、开放重定向、文件上传下载、命令执行、日志与凭据泄露
- 12.2 认证与会话安全：哈希算法与参数、密码令牌防篡改与撤销、并发与多端限制、防暴力破解
- 12.3 授权安全：默认拒绝、越权拦截与留痕、三权分立互斥、权限变更即时失效
- 12.4 数据与密码学：敏感字段加密与脱敏展示清单、密钥管理与轮换、SCC 边界、明文不落日志；**数据库凭据隔离**（迁移账号持有 DDL/DML，业务运行账号仅 DML，凭据分别入 Secret）
- 12.5 传输与证书安全：全链路加密、服务间通信证书、Nginx 证书与 CSR 流程（**BC 1.86 编解码 + 软件密钥签名**）；**12.5.2 Nginx 私钥两段式加密**（私钥 AES-256 → PKCS#8 加密 PEM 存 Secret；口令经 SCC 加密、由 **nginx 单容器内 wrapper**（`tini --` 作 PID 1（不用 `-g`，避免 TERM 广播导致 nginx fast shutdown）+ SCC CLI + shell，**无边车**）解密为**瞬时 tmpfs 文件**（写 → `nginx -t` → reload → **立即删除**，窗口毫秒级；Nginx OSS 只支持 `ssl_password_file`，无内存接口））；**12.5.1 私钥不可导出**（ADR-018：无导出接口、只出 CSR、密码令牌内 `CKA_EXTRACTABLE=false`、备份/恢复与 RTO 例外）；**按证书类型列私钥落位**（Nginx 证书 / 服务间证书 / CA 接入 / 上层应用接入），并指出 FR-CERT-004 的 CSR 是为 **Nginx 证书**服务；**SM2 本期不实施但须保留扩展点**（`Certificate`/CSR 算法枚举、`CryptoPort` 算法枚举、Nginx 国密版替换点）
- 12.6 审计与不可抵赖：操作日志覆盖清单（哪些动作必须留痕）、防篡改与留存、**逐条 `record_mac`（写入时计算）与转储包 manifest（条数 + SHA-256）**
- 12.7 文件与集成安全：上传校验、下载鉴权、SFTP/SNMP/CA 凭据与网络要求、**上层模块静态资源的目录隔离与同源风险**
- 12.8 安全配置基线：默认策略取值、必须修改项、上线检查表
- 12.9 容器与 K8s 安全：镜像最小化与扫描、**Secret 挂载与密钥不落镜像/ConfigMap**、ServiceAccount 与 RBAC 最小权限、NetworkPolicy 网络隔离、Pod 安全上下文、审计与集群侧日志
- 12.10 存量迁移安全：迁移通道与落盘加密、迁移账号最小权限与时效、迁移数据脱敏、迁移完成后旧环境数据销毁与留痕
